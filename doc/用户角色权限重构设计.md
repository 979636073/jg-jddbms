## 1. 当前实现

| 层次 | 当前机制 | 主要问题 |
| --- | --- | --- |
| 登录身份 | `sys_user` 登录，`getInfo` 返回角色和菜单权限，`getRouters` 按角色生成后台路由 | 业务模块还保留 `dbhub_user`、`role_code`、`team_user` 等旧模型；`ContextUtils` 已转而从 `sys_user` 构造登录用户，旧表与当前用户 ID 的语义需要清理和迁移 |
| 平台功能 | `sys_role`、`sys_menu`、`sys_role_menu`，后台接口使用 `@PreAuthorize` | 主要覆盖若依式系统管理；大量数据库工作区及业务接口没有对应的动作权限 |
| 数据范围 | 角色的 `dataScope` 按部门/本人过滤用户、角色等后台数据 | 与数据库、模式、表、SQL 操作的资源范围不是同一回事 |
| 数据源共享 | 数据源所有者/管理员可授权用户或团队；`data_source_access` 仅存数据源、对象类型、对象 ID | 只能表示“可进入”，无法区分查看、读数据、写数据、改结构、管理连接等 |
| 数据库权限 | 通过保存的 JDBC 账号连接目标库，由目标库最终允许或拒绝 SQL | 平台授权无法收窄已共享的高权限 JDBC 账号；数据库用户、对象权限页面管理的是目标库权限，不能当作平台角色 |

代码依据：`SysLoginController`、`SysPermissionService`、`PermissionService`、`ConnectionInfoHandler`、`DataSourceAccessBusinessServiceImpl`、`DataSourceSharingController`、`RdbDmlController`、`DataScopeAspect`。`DataSourceAccessCustomMapper.xml` 仍关联 `DBHUB_USER`，而共享界面用户搜索已使用 `SysUser`，这是统一身份时应核对的数据兼容点。

## 2. 优先解决的权限问题

1. **共享权限过宽**：用户/团队一旦获得数据源访问权，就可能使用该连接中的数据库账号执行其所允许的 SQL；`/api/rdb/dml/execute` 当前未检查平台级 `sql.execute` 或读写级别。危险 SQL 确认只处理提示，不等于授权。
2. **路由与接口权限断层**：后端 `anyRequest().authenticated()` 兜底只要求登录；部分页面写在 `constantRoutes` 中。菜单隐藏不构成安全控制，应逐接口校验。
3. **授权提升防护不足**：用户新增、修改和分配角色将客户端传来的 `roleIds` 传入服务层；需要明确校验操作者可分配的角色集合，并重新审计超级管理员保护、角色菜单授权和会话失效。
4. **旧模型混用**：`dbhub_user`/团队与 `sys_user` 的 ID 可能不一致，必须盘点实际数据后再迁移，不可直接把同一个数字当作同一个用户。
5. **审计不完整**：数据库操作日志、平台管理日志、授权变更日志需要统一记录操作者、数据源、动作、结果和关联请求；不能依赖页面是否显示按钮。

## 3. 目标权限模型

统一使用 `sys_user` 作为平台登录身份。权限判定为：**已认证且账号有效 ∧ 平台角色允许动作 ∧ 对指定数据源/资源有对应授权 ∧ 目标数据库账号本身允许操作**。默认拒绝；后端集中判定，前端只按判定结果控制入口。所有者身份仅自动拥有连接配置与共享管理权，不自动取得全部数据库操作权。超级管理员作为可审计的紧急授权，普通管理员不默认继承全部数据源数据权限。

权限分三层：

- **平台动作**：`user.manage`、`role.manage`、`audit.view`、`monitor.view`、`datasource.create`、`migration.run` 等，由平台角色决定。
- **资源动作**：按数据源授予 `metadata.read`、`data.read`、`data.write`、`schema.change`、`sql.execute`、`grant.manage`、`datasource.manage`。可先以数据源为粒度，后续按需要扩展至模式；禁止用菜单 ID 表示资源授权。
- **数据库原生权限**：达梦/Oracle 用户、模式、表、对象权限由目标库执行。平台可提供管理界面，但必须先具备平台资源权限，目标库再做最终校验。

自定义 SQL 难以靠简单文本识别安全地区分读写。初期建议把 `sql.execute` 作为单独的高风险权限；只读角色使用平台控制的只读查询接口及只读数据库账号。若必须让只读角色使用 SQL 编辑器，应增加服务端 SQL 解析、只读连接和事务只读防护，不能仅检查是否以 `SELECT` 开头。

### 推荐内置角色

| 角色 | 平台能力 | 数据源权限来源 | 默认限制 |
| --- | --- | --- | --- |
| 平台超级管理员 | 用户、角色、策略、系统设置及紧急维护 | 显式紧急访问，记录原因与审计 | 不作为日常账号 |
| 安全管理员 | 用户、角色、授权、审计 | 只能管理授权范围，不默认读取业务数据 | 不执行 SQL/迁移 |
| 数据源管理员 | 创建连接、维护自己负责的连接及共享 | 所有权或委派的 `datasource.manage` | 不默认执行 SQL |
| 数据库开发人员 | 工作区、结构查看、受控变更、查询 | 具体数据源授予 | SQL 执行单独授权 |
| 数据分析人员 | 工作区、元数据和数据查询 | 具体数据源授予只读 | 无写入、DDL、用户授权 |
| 审计员 | 审计日志、运行监控 | 授权范围内只读信息 | 无数据修改 |

角色是模板，是否能操作某个数据源仍由该数据源授权决定。一个用户可有多个角色；同一资源上的用户直接授权、团队授权和所有者授权取并集；禁用用户/团队立即失效。若需要明确拒绝规则，单独设计优先级，不在首版混入隐式 deny。

## 4. 后台重新设计

后台管理仅保留四个一级入口：

| 一级入口 | 内容 |
| --- | --- |
| 用户与权限 | 平台用户、角色模板、用户角色分配、数据源授权、团队（团队共享确实启用时） |
| 数据源控制 | 连接清单、所有者、共享情况、凭据轮换、授权记录 |
| 审计与运行 | 登录和操作审计、数据库运行告警、任务执行记录 |
| 系统设置 | 必要的安全参数、通知和维护配置；仅平台管理员可见 |

现有“数据库用户管理”和“对象权限”保留在工作区数据源树下，明确标注“目标数据库用户/权限”，避免与后台“平台用户/角色”混淆。数据迁移、表结构对比继续作为工作区工具，在目标角色授权后显示。

部门、岗位、若依数据范围、菜单配置、字典、公告、表单构建、代码生成、Swagger、Druid、缓存/服务器原始监控等先从普通后台导航移走。是否删除服务和表，应在查询实际使用方、定时任务与运维需求后逐项决定；字典与配置可能仍为系统依赖，不能仅凭菜单冗余就删库。菜单配置如仍需保留，应作为受限维护工具，而非日常权限编辑入口。

新的界面流程：用户列表直接显示状态、角色、可用数据源数、最近登录；用户详情分“基本资料 / 平台角色 / 数据源授权 / 操作记录”。角色页按业务动作分组展示权限矩阵，并预览该角色可见页面。数据源授权页以数据源为主，支持批量选择用户/团队、批量授予和撤销、有效权限预览、到期时间（可选），同时说明 JDBC 账号的实际权限。

## 5. 实施顺序

1. **盘点与安全基线**：导出实际 `sys_user`、`sys_role`、`sys_menu`、`sys_user_role`、`data_source_access`、`team_user`、`dbhub_user` 及连接所有者关系；列出所有业务接口与所需动作。先补角色分配越权校验、禁用用户会话失效和关键操作审计。
2. **统一身份与授权服务**：以 `sys_user.user_id` 为唯一平台主体，新建平台权限与数据源授权服务；给授权表增加动作集合、授权来源/操作者/时间等字段；迁移旧布尔共享记录时明确转换规则并保留可回滚备份。校正遗留的 `DBHUB_USER` 关联。
3. **业务接口接入**：按风险先管住 SQL 执行、DDL/DML、数据库用户与授权、迁移、任务、凭据及共享，再覆盖查询、监控和结构对比。每个接口明确资源 ID，不能信任前端传来的所有者或权限标记。
4. **重做管理界面与导航**：建立权限矩阵、数据源授权页和有效权限预览；移走冗余导航，保留兼容路由一段时间；权限不足时给出明确原因。
5. **迁移和清理**：用非管理员账号做正向与反向验收，验证多角色、团队、撤权、禁用、登录过期、直接调用接口、跨数据源和后台深链。确认实际使用方后清理旧身份模型、菜单和无用模块。

上线建议先以影子判定记录新旧结果差异，再对写操作启用新策略，最后覆盖读操作；撤权应清除缓存并使既有会话及时失效。保留旧表及脚本直至验收完成。

## 6. 验收标准

- 只读用户可查看已授权数据源的元数据和数据，不能通过 SQL、表编辑、迁移、任务或直接 API 修改数据。
- 未授权数据源在列表、直接 URL 和 API 中均不可见/不可访问；共享撤销后立即失效。
- 普通管理员不能给自己或他人分配更高角色，不能通过修改角色菜单、批量授权接口绕过限制。
- 数据库用户/对象权限操作同时通过平台授权与目标数据库授权；两种失败信息区分清楚。
- 每项授权、撤销、角色变更和高风险数据库操作可按用户、数据源与时间审计。
- 被隐藏的后台页面和接口都经过服务端验证；登录过期后所有独立标签页重新登录。

## 7. 待确认的产品规则

实施时只需确认三项业务策略：是否允许普通管理员跨所有数据源管理授权；是否开放任意 SQL 给非开发角色；是否保留团队作为长期授权主体。默认分别按“仅受委派范围”“不开”“保留”执行。
