# 项目整改审计与模块收敛记录

## 当前基线

- 构建方式：Maven 多模块，Java 8，Spring Boot 2.5.15。
- 当前根构建包含 12 个 Maven 工程：应用、公共库、框架、系统、业务、SPI、DM/Oracle 插件、Quartz、代码生成器。
- CodeGraph 已初始化；每次代码检索前先执行 `codegraph sync`。
- 基线验证：`mvn -o -DskipTests package` 通过。

## 当前模块结论

当前模块并非完全独立发布，主要依赖链为：

```text
admin
├── framework ── system ── common
├── quartz ──── common
├── generator ─ common
└── bisnuess ── system / spi / common / DM / Oracle
```

初步结论：

1. 不能直接把所有模块合并为一个模块。`bisnuess`、`spi`、插件之间存在明确的数据库方言和扩展边界。
2. `admin + framework + system + common` 具备合并为应用基础模块的条件，但应在测试和依赖收敛后执行。
3. `bisnuess + spi` 可作为数据库核心模块的候选合并对象。
4. `jd-dbms-plugins` 当前只纳入 DM 和 Oracle；Gbase、Kingbase、MySQL、Oscar 源码仍存在但未纳入根构建，暂不删除，需先确认产品支持范围。
5. `generator` 和 `quartz` 均被应用模块直接依赖，暂不能删除；后续按实际菜单、接口和任务配置确认是否内置或移除。

## 已完成的安全清理

- 删除 `jd-dbms-generator` 中确认无源码引用的 `commons-collections` 直接依赖。
- 删除根 POM 中仅供该依赖使用的 `commons.collections.version` 属性和依赖管理声明。
- `commons-collections` 仍可能作为 `commons-beanutils` 的传递依赖存在，不影响已有代码。
- 将业务模块中已废弃的 `${version}` 依赖表达式改为 `${project.version}`，避免 Maven 模型警告。
- 批量 SQL 结果保留整体失败状态和原始 SQL，移除未关闭的预编译语句。
- Blob、Clob 和字节数组读取增加流式处理及 256KB 限长。
- DBeaver 导入和在线升级 ZIP 增加路径穿越、条目数量和解压总大小限制。
- 用户修改或管理员重置密码后，清理该用户其他登录会话，当前会话可继续使用。
- 管理员重置密码和个人修改密码均纳入统一 Token 会话失效处理。
- 授权、函数、存储过程和触发器共用的 JDBC 执行入口修复结果丢失问题，失败时返回明确错误信息。
- 数据库批量导出异步任务修复失败状态被覆盖为 `FINISH` 的问题，异常统一落库为 `ERROR` 并保证上下文清理。
- 数据库导入和 DMP 导出异步回调修复失败状态丢失问题，失败结果保留在缓存中供前端查询。
- 任务下载校验任务归属时改用安全的对象值比较，并拒绝空/不可读文件。
- 数据库和表导入日志下载仅在文件成功读取后删除缓存，文件缺失时保留任务记录便于排查。
- 表数据导入限制资源路径必须位于 `dbms.profile` 目录内，阻断路径穿越；异步异常统一记录为 `ERROR` 并清理线程上下文。
- 统一列表结果错误语义：`ListResult.error(...)` 与 `DataResult.error(...)` 一致返回 `success=false`，避免失败请求被前端误判为成功。
- 统一 SQL 执行结果聚合：无论是否存在列头，单条失败都会上报为列表失败；DML 执行与执行计划接口复用同一结果转换逻辑，完整保留错误字段。
- 修复 DDL 单项失败被 `DataResult.of(...)` 包装为成功的问题，并处理空结果集，统一返回明确失败状态。

## P2 已完成项（核心能力统一）

- SQL 执行结果统一由 `SQLExecutor` 生成逐条结果，服务层无列头时也会聚合失败状态。
- DML 执行与执行计划接口复用统一的 `ExecuteResult` 到 `ExecuteResultVO` 转换逻辑，保留完整错误字段。
- DDL 执行在空结果、单项失败场景返回明确失败状态，不再使用成功包装器掩盖错误。
- 统一 `DataResult`、`ListResult` 的失败语义，避免前端误判。

P2 暂不继续合并模块或删除 DTO/VO：当前仍存在前端接口、Spring 扫描、插件 SPI 和数据库方言边界，需在 P3 以调用清单和冒烟测试为准逐步收敛。

## P3 阶段进展（模块收敛评估）

- 已确认 `admin → framework → system → common` 为单向依赖链，无模块循环依赖。
- 启动类由 `@SpringBootApplication` 自动扫描 `com.jd`，额外扫描仅保留 `com.easy.cas.client`，避免重复扫描主工程。
- `common` 当前同时承载 Redis、MyBatis、JDBC、文件和通用 Web 能力，不满足“纯基础模块”条件，暂不与 `system/framework/admin` 直接合并。
- `framework` 包含 Mapper 扫描、AOP、Web 配置和拦截器，属于运行时基础设施，需保留独立边界。
- P3 下一步：建立各模块对外 API/配置/SPI 清单，在不改变启动行为的前提下评估 `system + common` 的内部包分层，再决定是否物理合并。

## P3 边界清单与依赖验证（2026-08-28）

### 模块职责与边界

| 模块 | 当前职责 | 对外边界 | 结论 |
|---|---|---|---|
| `jd-dbms-common` | 通用返回结果、上下文、JWT/安全、Redis、文件、基础配置和 Web 公共依赖 | 被 system、framework、quartz、generator、spi、bisnuess 直接依赖 | 保留独立模块；只能做内部包分层，不能整体并入 system |
| `jd-dbms-system` | 用户、角色、菜单、字典、部门等系统领域服务及 Mapper | 依赖 common；由 framework 间接装配 | 保留独立模块；可评估与 common 的领域/基础包分离 |
| `jd-dbms-framework` | Spring Web、AOP、Druid、验证码、资源、拦截器、Mapper 扫描 | 依赖 system；被 admin 作为运行时基础设施引入 | 禁止并入 common；保留独立配置边界 |
| `jd-dbms-admin` | Spring Boot 启动入口、管理端控制器、Web 打包和外部 CAS 扫描 | 聚合 framework、quartz、generator、bisnuess | 保留应用壳；不下沉业务代码 |
| `jd-dbms-bisnuess` | 数据源、数据库对象、SQL/DML/DDL、任务、导入导出等业务服务 | 依赖 common、system、spi、数据库插件 | 保留业务模块；不可与 admin/framework 合并 |
| `jd-dbms-spi` | 数据库模型、MetaData、SqlBuilder、SQLExecutor、驱动扩展接口 | 被 bisnuess 和插件实现依赖 | 保留 SPI 独立性；不可并入 bisnuess |
| `jd-dbms-plugins` | DM、Oracle 等数据库方言插件聚合 | 仅通过 SPI 接入 | 保留插件隔离；按产品支持范围逐个评估 |
| `jd-dbms-quartz` | 定时任务配置和执行 | 依赖 common，被 admin 引入 | 暂不删除或并入，需先核实任务配置引用 |
| `jd-dbms-generator` | 代码生成控制器、服务和模板 | 依赖 common，被 admin 引入 | 暂不删除或并入，需先核实前端路由和权限 |

### 直接依赖方向验证

根据各模块 POM 的 `com.jd` 依赖解析，当前方向为：

```text
admin ──> framework ──> system ──> common
  │          │             
  ├──────> quartz ───────> common
  ├──────> generator ────> common
  └──────> bisnuess ─────> common / system / spi / plugins
spi ─────> common
plugins ─>（无源码依赖）
```

- 未发现 `common → system/framework/admin` 的反向 Maven 依赖。
- 未发现 `system ↔ framework` 或 `bisnuess ↔ spi` 的 Maven 循环依赖。
- `jd-dbms-plugins` 为聚合 POM，实际插件通过 SPI 实现数据库方言。

### Spring、Mapper 与 SPI 验证

- 启动类位于 `admin`，由 `@SpringBootApplication` 扫描 `com.jd`，另补充扫描 `com.easy.cas.client`。
- `framework` 的 `ApplicationConfig` 统一执行 `@MapperScan("com.jd.**.mapper")`；system、bisnuess、quartz、generator 均包含 Mapper，不能移除该配置。
- `framework`、`admin`、`common`、`quartz`、`generator`、`bisnuess` 均包含 Spring 配置或组件；不能按“无 Controller”简单删除。
- `spi` 本身无 Spring 组件，承担模型、接口和执行器；插件实现依赖其扩展边界。

### 依赖验证结果与限制

- 已执行 `codegraph sync`，索引为最新；CodeGraph 未发现上述模块的反向调用闭环。
- 已执行 Maven 依赖树尝试。由于离线模式下 reactor 子模块尚未安装到本地仓库，`dependency:tree` 在 `jd-dbms-system` 解析 `jd-dbms-common:3.8.7` 时被 `local-assets` 仓库阻断；该失败不代表依赖冲突。
- 已通过 POM 静态解析复核所有 `com.jd` 直接依赖方向，并以完整构建作为最终一致性验证。

### 当前决策

1. `admin/framework/system/common` 暂不物理合并；先进行 `common` 内部基础能力、Web 能力和持久化能力分层。
2. `bisnuess/spi` 暂不合并；SPI 与数据库插件必须保持独立版本边界。
3. `quartz`、`generator` 暂不删除；继续核对前端路由、权限、配置和反射引用。
4. 下一步仅允许在满足删除准入条件且完整构建通过的前提下做单模块、单依赖变更。

## 参考项目可吸收能力

优先吸收以下设计，而不是直接复制代码：

1. 连接档案与运行时连接分离，连接密码加密保存，连接按用户隔离。
2. 统一 `Conn-Id`/连接上下文，所有业务接口显式校验连接权限。
3. SQL 控制台支持单条、脚本、批量、执行计划、格式化、手动事务和异步日志。
4. 表数据编辑支持分页、批量保存、LOB 限制和导入导出。
5. ER 图、结构迁移、数据迁移、结构/数据对比、备份恢复和任务中心。
6. 批量 DDL、授权、迁移统一返回逐项成功/失败结果，不返回含糊的“整体成功”。
7. 大文件采用流式处理，ZIP 解压增加条目数、单文件大小和总大小限制。
